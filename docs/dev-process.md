## 第一章 文档矩阵

本项目所有文档分为五层，**每一层有明确的角色与读者**：

| 文档 | 路径 | 回答的问题 | 更新频率 | 主要读者 |
|---|---|---|---|---|
| **项目设计报告（PRD）** | `docs/project-design-report.md` | 做什么 & 为什么 | 低（设计变更时） | 产品/项目所有人 |
| **技术设计文档** | `docs/tech-design.md` | 怎么做 & 怎么做好 | 低（架构变更时） | 工程师 |
| **开发流程规范（本文件）** | `docs/dev-process.md` | 按什么流程做 | 极低（流程变更时） | 所有人 |
| **开发计划表** | `docs/dev-plan.md` | 现在做什么 & 做到哪了 | 高（每 Sprint/任务更新） | 所有人 |
| **开发记录** | `docs/dev-log.md` | 过去发生了什么 & 为什么 | 高（每次决策/问题记录） | 所有人 |

## 第二章 强制读取流程

> **核心规则**：每次开始任何开发动作前，**必须先读这四份文档的对应部分**。
> 不是建议，是流程。

### 2.1 开始开发前（必读）

**第一步**：读 [开发计划表](dev-plan.md)

- 找到当前 Sprint 在做什么
- 确认要做的任务已经在表中，且状态是「⚪ 待开始」或「🟡 进行中」
- 如果没有，先把任务加到 Dev Plan，再开始

**第二步**：读 [开发记录](dev-log.md) 最近 10 条

- 了解上次/上上次会话发生了什么
- 是否有遗留问题、阻塞、未完成的工作
- 是否有与当前任务相关的历史决策需要遵守

**第三步**：按需读 PRD / Tech Design

| 当前任务类型 | 必读 |
|---|---|
| 新增功能模块 | PRD §2.2 功能清单 + Tech Design §4 模块 API |
| 调整 UI/UX | PRD §2.4 信息架构 + §2.5 关键交互流程 |
| 修改 Prompt 逻辑 | PRD §4.1 灵魂定制 + Tech Design §6.1 Prompt 编译 |
| 修改存储 schema | Tech Design §5 数据模型 + §13.1 迁移策略 |
| 修改构建/部署 | Tech Design §12 构建与部署 |
| 修改测试策略 | Tech Design §9 测试策略 |
| 不确定时 | **任何不确定的情况，先读再问** |

### 2.2 读取失败的处置

如果发现：
- 文档与代码不一致 → 先记录到 Dev Log，再决定要不要改文档
- 文档缺失某项设计 → 先记录到 Dev Log，标注「需补设计」，不要靠猜
- 文档与新需求冲突 → 不要直接改文档，先在 Dev Log 提「设计变更需求」，让用户决策

### 2.3 任务结束 checklist

> ⛔ **强制规则**：**每一个开发任务结束**（无论成功、失败、阻塞、取消），都必须完成以下 3 件事。
> 不允许「做完就忘」——这是流程闭环的关键。

```
┌────────────────────────────────────────────────────────┐
│  ✅ 任务结束 checklist（每次必做）                      │
│                                                        │
│  □ 1. 写 Dev Log                                       │
│     · 类型：✅ 进度（或 ⚠️ 问题 / ❌ 取消）             │
│     · 关联：本任务的 Dev Plan 任务 ID                   │
│     · 内容：完成情况、验证结果、未完成项                 │
│                                                        │
│  □ 2. 更新 Dev Plan                                    │
│     · 状态：🟡 → ✅（或 🔴 / ❌）                       │
│     · 「验证结果」列：填写具体的验证证据                 │
│     · 备注：如有遗留项，写明                             │
│                                                        │
│  □ 3. 自检                                               │
│     · 是否有未记录的决策？补一条 📌 决策                 │
│     · 是否有遇到的问题？补一条 ⚠️ 问题                   │
│     · 是否需要新增后续任务？追加到 Dev Plan             │
└────────────────────────────────────────────────────────┘
```

**为什么强制**：

1. **Dev Log 是上下文恢复的载体** —— 下次打开项目，第一件事就是看最近做了什么；
2. **Dev Plan 是当前焦点的镜子** —— 不更新的计划表会迅速过期、失去指导意义；
3. **三件事一起做才能闭环** —— 只更新一个，等于任务没真正结束。

**例外情况**：

- 如果任务**被取消**，同样要更新 Dev Plan（状态 → ❌）和 Dev Log（说明取消原因）；
- 如果任务**阻塞中**，要写 🔴 状态 + 在 Dev Log 写 ⚠️ 问题（说明阻塞原因）。

## 第三章 强制记录时机

> **核心规则**：三类时刻必须写开发记录。
> 不是建议，是流程。

### 3.1 何时写 Dev Log

| 触发条件 | 类型 | 示例 |
|---|---|---|
| 做出架构/技术选型决策 | 📌 **决策（Decision）** | 「决定用 IndexedDB 而非 LocalStorage 存向量，原因……」 |
| 推翻既有设计 | 📌 **决策** | 「决定放弃自定义 TTS 引擎，全部用 Web Speech」 |
| 引入新依赖 | 📌 **决策** | 「引入 @ricky0123/vad-web@0.0.x 用于前端 VAD」 |
| 遇到阻塞性问题 | ⚠️ **问题（Issue）** | 「LanceDB WASM 在 Safari 加载失败，原因……」 |
| 发现 bug | ⚠️ **问题** | 「Prompt 编译时 personality 字段为空导致崩溃」 |
| 学到新经验 | 💡 **教训（Lesson）** | 「教训：每次新增 Schema 字段必须配套 migration」 |
| 完成 Sprint 任务 | ✅ **进度（Progress）** | 「M1-001 项目脚手架已完成，验证：dev server 启动 OK」 |
| 用户给出新需求/调整 | 📥 **需求（Requirement）** | 「用户要求：灵魂编辑器需要支持拖拽排序」 |
| 文档与代码偏差被发现 | 🔄 **同步（Sync）** | 「PRD §2.2 中 F-005 描述与代码不一致，已同步」 |

### 3.2 何时更新 Dev Plan

| 触发条件 | 操作 |
|---|---|
| 开始一个任务 | 状态：⚪ → 🟡 |
| 完成一个任务 | 状态：🟡 → ✅，填写验证结果 |
| 阻塞一个任务 | 状态：🟡 → 🔴，记录阻塞原因到 Dev Log |
| 发现需要新增任务 | 追加任务条目，状态 ⚪ |
| 发现任务可以删除/合并 | 删除或合并，状态 → ❌ |
| 完成当前 Sprint 所有任务 | 创建新 Sprint 段 |

### 3.3 Dev Log 条目格式

```markdown
## [YYYY-MM-DD] [一句话标题]

**类型**：📌决策 | ⚠️问题 | 💡教训 | ✅进度 | 📥需求 | 🔄同步
**相关任务**：[关联的 Dev Plan 任务 ID] 或 [无]
**相关文档**：[关联的 PRD/Tech Design 章节] 或 [无]

**背景**：
[为什么会有这件事，1-3 句]

**决策/发现/进展**：
[具体内容，3-10 句]

**影响**：
[影响了哪些文件、计划、决策]
```

## 第四章 变更控制

> **核心规则**：PRD / Tech Design 的任何变更必须留痕。

### 4.1 设计变更的三档处理

| 变更类型 | 处理方式 |
|---|---|
| **小调整**（字段名、措辞、顺序） | 直接改文档，并在文档变更记录中加一行 |
| **中变更**（新增字段、新增模块、新增 ADR） | 改文档 + 在 Dev Log 写一条「🔄同步」记录 + 通知用户 |
| **大变更**（推翻既有架构、改核心数据模型） | 先在 Dev Log 提「📥需求」记录 → 用户确认 → 改文档 → 在 Dev Log 写「🔄同步」 |

### 4.2 偏离设计的处理

如果实施中发现原设计不可行：

```
1. 不要默默改代码（熵增）
2. 先在 Dev Log 写 ⚠️ 问题 + 提出替代方案
3. 让用户决策
4. 决策后改文档（同步）+ 改代码
```

### 4.3 文档与代码同步检查

每个 Sprint 结束时做一次：
- Dev Plan 中 ✅ 任务对应的代码，是否符合 PRD/Tech Design 描述？
- 如有偏差，写一条 🔄 同步记录

## 第五章 任务生命周期

### 5.1 任务状态机

```
    ⚪ 待开始
      │
      │ (开始)
      ▼
    🟡 进行中
      │
      ├──► 🔴 阻塞 ──► (解除阻塞) ──► 🟡 进行中
      │
      │ (完成)
      ▼
    ✅ 已完成
      │
      │ (发现需要返工)
      ▼
    🟡 进行中

    ❌ 已取消（任务被合并/拆分/废弃）
```

### 5.2 任务粒度

- 每个任务应该能在 **1 个工作日内完成**（最长不超过 2 天）
- 超出粒度的任务必须拆分
- 每个任务必须有 **可验证的完成标准**

### 5.3 Sprint 节奏

- **Sprint 长度**：1 周（个人 Demo）或 2 周（团队）
- **Sprint 计划**：每个 Sprint 开始时确定 3-7 个任务
- **Sprint 回顾**：每个 Sprint 结束时更新 Dev Plan，标注进度，写一条 ✅进度 记录到 Dev Log
